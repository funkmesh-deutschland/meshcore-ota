# Tests

## Simulation

```
make -C sim test MESHCORE=<path to MeshCore> PYTHON=python3
```

Requirements:

- a C compiler (`cc`),
- a checkout of MeshCore, from which the Ed25519 verification in `lib/ed25519` is compiled,
- Python 3 with the packages from `tools/requirements.txt`.

The simulation compiles the core from `core/` unchanged for the host and emulates the flash: writing can only clear bits, erasing affects whole pages. A run takes a few minutes.

| Test | What it checks |
| --- | --- |
| `test_sha256` | SHA-256 of the core against known values |
| `test_inflate`, `check_deflate.py` | decompression and compression of the core, cross-checked with zlib |
| `apply_check` | a package from `tools/mcota.py`, applied with the device code, yields the new firmware |
| `test_boot` | swap and rollback of the loader. Power fails at every single write and erase operation, after which both slots have to be correct |
| `test_compact` | rebuild without a second slot using all three methods, also with a power failure at every point. No word in flash may be written more often than permitted |
| `test_node` | distribution along a chain of repeaters with packet loss and corrupted packets, overhearing, switching the provider, fetching missing blocks, two packages in succession, keeping to the airtime. Repeaters with a foreign key or a different device type must not accept anything |
| `test_esp` | switch without a loader as on the ESP32, with a separate package store and with the package at the end of the other partition |
| `test_provider.py` | the provider of the program against the device code (`node_stdio`), directly and over 2 hops, plus query and hello |
| `test_companion.py` | the companion interface against an emulated companion on a serial port |

The test data in `sim/fixture/` is generated by `make_fixture.py` on the first run. `make -C sim clean` removes it together with the compiled tests.

On GitHub the same tests run on every push to `main` and on every pull request, against MeshCore at commit `75b04ef`.

What the simulation does not cover: the jump of the loader into the firmware, writing to real flash, the radio and the interaction with MeshCore on the device.

## Testing on devices

The procedure below applies to two Seeed Xiao nRF52840, both reachable over USB. Before every transmission test an antenna has to be connected to both devices.

### Test firmware

With the program, including key and presets:

```
meshcore-ota install Xiao_nrf52_repeater --version v1.17.1 --test
meshcore-ota install Xiao_nrf52_repeater --version v1.18.0 --test
```

The test firmware (`--test`) transmits with 5 % instead of 0.5 %, offers at shorter intervals (15 seconds to 2 minutes) and waits 2 instead of 30 minutes before applying on its own. Its build name carries the suffix `-test`. Sending then requires `--test` as well.

By hand, without the program:

```
TAG=v1 ./firmware/build.sh
TAG=v2 ./firmware/build.sh
```

The script needs PlatformIO (`PIO`), Python (`PYTHON`) and `arm-none-eabi-gcc` (`CROSS`). It checks out MeshCore at the pinned commit to `build/MeshCore`, applies `firmware/meshcore.patch` and builds the repeater firmware and the loader. Afterwards `build/out` contains, for each build, a `.bin` (the firmware alone) and a `.uf2` (loader, firmware and blank status pages). By default it builds the environment `Xiao_nrf52_repeater_mcota_test`, with `ENV_NAME=Xiao_nrf52_repeater_mcota` the one with 0.5 %. Firmware built this way does not carry a key.

### Recovery

Press the reset button twice in quick succession. The device shows up as a USB drive and accepts any UF2 file, including the ordinary MeshCore firmware. The loader and the firmware do not write to the bootloader area.

### Step 1: First installation

1. Double reset, then copy the UF2 file from `install/` (or `build/out`) to the drive. On both devices.
2. Check over USB:

```
meshcore-ota cli --port /dev/ttyACM0 ota info
```

Expected: `OK fw=<build> idle ...`. This shows that the loader jumps into the firmware and the firmware runs at its address.

3. Check the radio: both devices have to use the same radio parameters and see each other as neighbours (`neighbors`).

### Step 2: Key

`ota key` shows the key IDs. Firmware from the program already carries the key. For firmware from `build.sh`:

```
meshcore-ota keygen test.key
meshcore-ota cli --port /dev/ttyACM0 ota key set 1 <public key>
meshcore-ota cli --port /dev/ttyACM1 ota key set 1 <public key>
```

Without a key a device accepts nothing.

### Step 3: Loading the package onto the first device

Over USB:

```
meshcore-ota pack --key test.key --old old.bin --new new.bin --board xiao_nrf52 --version v2 --build 2 --out v1-v2.mcota
meshcore-ota load --port /dev/ttyACM0 v1-v2.mcota
```

Expected on device A: `ota info` reports `ready v2` and all pages.

Or, with firmware from the program, over the air through a companion:

```
meshcore-ota update --serial /dev/ttyACM2 --test
```

### Step 4: Transfer over the air

Device B fetches the update from device A by itself. `ota info` on B shows the progress (`loading v2 n/m`), and `ready` at the end. On A the counter `tx` increases, and `ota peers` shows B with the number of pages it is still missing.

To check:

- B becomes complete.
- A device without a key or with a different key fetches nothing.
- After a reset of B in the middle of the transfer it continues from where it was.

### Step 5: Applying

B applies a package with `--auto-apply` (the default with `meshcore-ota update`) on its own as soon as it is complete and the waiting time without a request from a neighbour has elapsed. Otherwise by hand:

```
meshcore-ota cli --port /dev/ttyACM1 ota apply
```

Device B reboots, the loader swaps, and afterwards `ota info` reports: `fw=v2 ... loader=trial`. As soon as B has heard a reply from a neighbour and has been running for one minute, it changes to `loader=confirmed`. Any MeshCore repeater in range counts as a neighbour.

### Step 6: Power failure and rollback

- Pull the plug during the swap and plug it back in. Expected: the loader completes the swap, and v2 is running.
- Switch off device A and all other repeaters in range, then apply on B. Expected: B receives no reply, reboots after 10 minutes each time and runs v1 again after three trial boots. `ota info` reports `failed ... loader=rollback`.

### Step 7: Route over hops

With `--route` a route over hops can also be checked on the bench, for example `--route 1a2b3c4d=5e` for the repeater whose key begins with `1a2b3c4d`, via the repeater with the hop `5e`. MeshCore keeps to the fixed route even if the target could be reached directly.

The commands on the repeater are described in [app.md](app.md).
